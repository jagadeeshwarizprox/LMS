# Change set, 2 September 2026 (second pass)

Everything here comes from the review in `PIB_LMS_Review_2026-09-02.md`. Nine items, taken
in the order the review ranked them: the things that were broken in production first, the
things that were quietly wrong second.

**The backend now compiles for real.** `javac` over all 180 sources at the Java 17 target,
with the third-party surface stubbed: 208 classes written, zero errors. That has never been
true before in this project, and getting there found a defect no structural checker could
see. It is item 0 below.

---

## 0. A missing import that would have failed the first Maven build

`MentorController` declared and injected `ProjectRunService` and never imported it. The
class could not compile. Every checker in `tools/` passed it, because they read the source
as text and reason about structure; none of them resolves a symbol.

This is exactly the class of error the review said only a real compile catches, and it was
sitting in the shipped build. The import is added and the whole tree now compiles.

What is still unverified is whether the stubs match the real jars. `mvn clean package` on a
networked machine remains the one outstanding check.

---

## 1. Moving a learner between batches now moves their mentor

The rule is that a batch has one mentor and every learner in it is theirs.
`MovementService.applyBatch` set the batch, the WhatsApp link and the induction gate, and
never touched `mentorId`. A learner moved from B56 to B57 sat on B57's roster while still
reporting to B56's mentor, so the mentor's batch view and their learner list disagreed and
neither was wrong.

- `applyBatch` sets the mentor from the batch, on every placement and every track change.
- The change writes a `MentorAssignment` history row, so it reads back like any other
  mentor change rather than appearing to have happened by itself.

**The duplicate path is gone.** There were two endpoints for the same operation:
`POST /admin/learners/{id}/batch` (`placeInBatch`, unused by the UI, no reason recorded, no
audit row) and `POST /admin/learners/{id}/move-batch` (`changeBatch`, which the UI calls).
Both carried the same bug. `placeInBatch` and its endpoint are deleted.

## 2. A mock interview can be finished

`POST /mentor/mocks/{id}/record` existed, carried score and feedback, and was called by
nothing. The queue only fetched `PENDING`, so a mock disappeared from the mentor's screen
the moment it was scheduled: there was nowhere left to say what happened. Every mock in the
product would have sat `SCHEDULED` for ever, `score` and `feedback` written by no code path
at all, and `mocksDone` on the call brief counting something that could never increase.

- The queue carries pending **and** scheduled, held ones first.
- **Record outcome** on a scheduled mock: score out of 100 and a note, both required. A
  score with no note is nothing a learner can act on.
- **Decline** on a pending one, with a reason, because declining is a real answer.
- Both mail the learner. A recorded mock cannot be recorded twice.

## 3. The project system is reachable

The largest subsystem in the product had no way to enrol anybody. Four working endpoints
sat with no screen behind them, so however good the catalogue was, the learner workspace
polled an empty list for ever and the mentor review queue was permanently empty. The
lifecycle rule that an approved project opens the batch mock could never fire, which meant
batch learners could not reach a mock at all.

New `/admin/projects`, routed and in the sidebar, the mobile nav and the command palette:

- **Enrol a cohort** in one action. Anyone already on the project is skipped, so running it
  again after a batch move is safe.
- **Enrol one learner**, for premium, where a project is paced to the person.
- **The batch grid**: one row per learner, one square per stage, with the stage key and
  overdue state. A column of amber is a stage the mentor is behind on; a row of grey is
  somebody who stopped.

Enrolment sits with admin rather than in the builder because it is an operations decision,
the same shape as a batch move. Nothing advances a stage from this screen: that stays with
the mentor, which is what makes the grid mean anything.

## 4. One at-risk rule

There were three definitions. `MentorService.isAtRisk` and `atRisk` agreed with each other
and honoured `lms.at-risk.no-login-days`. `MentorDeskService.row` had a third, hardcoded:
seven days regardless of the setting, plus "no study minutes this week", which on a Monday
morning flags the entire cohort.

The roster is the screen mentors spend their day on, so the setting the execution guide
tells an admin to configure was the one thing it ignored.

- `riskReasons(Learner)` on `MentorService` is now the single definition, returning the
  reasons rather than a bare boolean.
- `isAtRisk` and `atRisk` are both built from it, and the roster calls it.
- The week's study minutes are still on the row as their own number, which is where that
  signal belongs.
- The roster now carries `riskReasons` too, so it can say why rather than just flag.

## 5. The chapter test actually gates

`passMark` (60) and `attempts` (2) were editable per chapter and read by nothing. There was
no attempt cap, and `chapterComplete` asked only whether a score existed:

```java
if (c.getTest().isEnabled() && p.getQuizScore() == null) return false;
```

So a learner scoring zero completed the chapter and unlocked the next one. The test was
decorative.

- The attempt limit is enforced, and passing early stops further attempts.
- `chapterComplete` requires a score **at or above the chapter's pass mark**.
- **The best attempt counts, not the first.** Keeping the first was the harsher half of two
  policies at once: the score was frozen on a bad day while nothing stopped the learner
  moving on regardless. A retake that cannot change the outcome is busywork.
- The learner is told the pass mark and how many attempts remain *before* they sit it. A
  limit nobody can see is a trap, not a rule.
- `POST /mentor/learners/{id}/chapters/{chapterId}/reopen-test` clears the attempts, with
  the same ownership check as every other mentor action. A limit has to be reachable, and a
  learner who reaches it needs somewhere to go that is not a support ticket.

## 6. Teach back no longer scores by word count

The Ollama fallback was `words * 100 / 80`, capped at 100. Eighty words of anything scored
full marks. A restart or a busy GPU silently turned the AI assessment into a length check,
and the only trace was a `gradedBy: "rubric"` string that no screen displayed. A mentor
could not tell an AI-graded 85 from a counted one.

- When the model is unreachable, **nothing is scored**. The answer is saved and held
  `conceptCheckPending`.
- The chapter still opens on it, because the learner did the work and the model being down
  is not their fault.
- The answer itself is stored on the progress row, so it can be read or regraded.
- The learner is told plainly that it is waiting to be read rather than scored.
- The mentor's Learning tab shows a **Teach back ungraded** tag carrying the answer.

## 7. Booking the onboarding call no longer clears the gate

`bookSlot` set `gateCallDone = true` the moment the booking row was written. A premium
learner booked a slot, never appeared, and their modules opened. For a track whose entire
premium is the human contact, this was the gate that matters most and the weakest one in
the product. Attendance was already being recorded and simply was not connected to it.

- `ScheduleService.mark` clears the gate on **PRESENT** or **LATE**.
- Marking somebody **ABSENT** takes it back, because a session they did not attend has not
  happened for them. Nothing else on their record is touched.
- Both directions are written to the activity log.
- `markInductionDone` still clears the cohort, but skips anyone a mentor has already marked
  absent on an induction slot for that batch. Marking the session done asserts that it ran,
  not that everybody was in it, and overwriting a recorded absence throws away the better
  evidence.

## 8. Onboarding and induction are two different sessions again

They were one slot kind, `ONBOARDING`, labelled **"Onboarding call"** on the mentor's
screens and **"Induction"** on the admin board. Two different things in the lifecycle
document and one value in the code, which meant a premium learner in scope who booked a
batch induction created from the board cleared their premium onboarding gate.

- `INDUCTION` is now its own slot kind. It already existed as a *recording* kind, so the
  vocabulary was half split already.
- `ONBOARDING` is the premium one to one; `INDUCTION` is the batch group session. The gate
  logic in item 7 treats them separately and checks the learner's track before acting.
- `ONBOARDING` is deliberately removed from the publishable recording map: a premium one to
  one is not library content. An induction still publishes as before.
- Both appear in the board, the mentor slot form, the schedules form, the attendance screen
  and the learner's session list, under their own names.

- **One course per learner.** `bundleId` is a single string and `changeBundle` replaces it,

`mvn clean package` on a networked machine is still the one check that has not run.

# Third pass, same day

Four more from the review's decision list. The remaining three are named at the end with
what each one needs from you.

## 9. Recording coverage is gone; Access is narrowed

The 31 August instruction was that Access sharing and Recording coverage should be
removed. The 2 September build created both, under the heading "the 404s are gone" — they
were 404s because they were meant to be gone.

**Recording coverage is removed** in full: the page, the route, all three nav entries, the
document title, the `/admin/recording-coverage` endpoint and the `RecordingService.
coverage()` method behind it. It was a report, and the same data is on the mentor
recordings screen.

**Access is not deleted, and that is a judgement I am flagging rather than burying.** The
page you asked to remove was a sharing surface; what carries that route now is four
things, two of which have no other home in the product: video rotation, which is the answer
to a leaked link and the thing your video protection work depends on, and the sign-in
lockout list with its unlock. Deleting the page would strand every locked-out account with
no way back in. So it is renamed **Video security** everywhere and the sharing framing is
gone. Say the word and it goes entirely, but tell me where you want rotation and unlock to
live first.

## 10. The feature toggles do something

`FeatureService.enabled()` had no callers anywhere. Nine of thirteen keys were read by
nothing at all, so an admin switching one off on Track features changed nothing and had no
way to discover that.

New `FeatureService.require(learner, key, message)`, which refuses rather than returns, and
the checks are on the server. Hiding a button is presentation; refusing the request is the
rule.

| Key | Now enforced at |
|---|---|
| `jobs_referrals` | `GET /learner/jobs` |
| `case_studies` | `GET /learner/case-studies` |
| `biweekly_call` | `GET /learner/calls` |
| `ai_teach_back` | `POST /learner/chapters/{id}/concept-check` |
| `one_to_one_booking` | `POST /learner/slots/{id}/book` |
| `cohort_pace` | batch payload, computed only when on |
| `batch_leaderboard` | batch payload, computed only when on |

`one_to_one_booking` replaced a hard-coded "batch cannot book" test. That was the default,
not the rule: a batch learner granted it individually now gets it, and premium can have it
withdrawn, which is what a per-learner override is for.

Cohort pace and the leaderboard are not computed at all when off, so the numbers never
leave the server. The learner's batch page draws neither when they are absent, rather than
rendering an empty table.

Still unenforced, and honestly so: `live_sessions`, `doubt_clearing`, `group_doubt`,
`industry_sessions`, `project_sessions`, `induction_gate`, `top10`. The first five want a
filter on the session board's audience logic, which is a design question rather than a
guard. `top10` has nothing behind it to gate.

## 11. A batch can be edited and closed

`createBatch` and `induction-done` were the only writes. A batch's mentor could never be
changed after creation, so if a mentor left, every learner had to be moved one at a time.
A wrong start date could not be corrected and a WhatsApp link could not be added later.

- `POST /admin/batches/{id}` — name, mentor, start date, WhatsApp and community links.
  Anything omitted is left alone. **Changing the mentor moves the whole cohort**, with a
  `MentorAssignment` row per learner, because that is what a batch mentor means.
- `POST /admin/batches/{id}/open` — close a batch to new joiners, or reopen it.
- Both on the Batches screen, with an Intake column showing open or closed.

`Batch.open` existed and was never set false anywhere in the codebase, so no batch ever
closed. The Wednesday auto-placement rule filters on it, which after a year would have
meant choosing among fifty live batches, and every batch dropdown listing all of them.

Closing is about intake only. Nobody is removed, no progress is touched, mentors keep their
learners: the batch simply stops being a destination.

## Left, and what each needs

- **One course per learner.** `bundleId` is a single string and `changeBundle` replaces it,
  so an upsell erases the first course and its progress rows point at chapters no longer in
  the bundle. This is a data-shape change with a migration attached; it wants your decision
  on whether a learner holds many courses at once or one at a time, before code.
- **Certificates.** Asked for on the intake form, promised on the course screen, absent
  everywhere. The screen also says "issued after the last assignment is approved", which
  contradicts the signed rule that an admin issues them. Needs the template and who signs
  it before it can be built.
- **Session mail and a template store.** Releasing a week tells nobody. `cancel()` carries a
  comment saying the booker will be told and sends nothing. Every subject and body is a
  string literal inside a service, so changing the credential mail is a redeploy.
- Admin reports, learner results, premium leaderboard, top 10, the Google Sheets adapter,
  server-side topic completion.

`mvn clean package` on a networked machine is still the one check outstanding. The offline
compiler resolves every symbol in our own code — 180 sources, 208 classes, zero errors —
but it cannot see a Spring or POI signature that has drifted from the real jar.

# Fourth pass: the shared week

## 12. Every mentor can now see and run the week

The weekly cadence engine already existed and was good: `SessionSchedule` holds a
repeating session with a **host rotation**, a nightly cron generates the actual sessions
two weeks ahead, `openToAllBatches` already models "any batch or premium can join", and
the board releases a whole week in one action.

The problem was who could open it. **The board was admin only**, so the org's cadence lived
somewhere the people delivering it could not see. A mentor had two half screens instead:
one for repeating sessions, one for their own slots, and neither showed the week those
screens produced. The person taking Thursday's doubt clearing could not see that somebody
else had already taken it.

**One week, one screen, for everyone who runs a session:**

- `/api/week` — the same week for mentors and admins. What changes by role is what you may
  do to a row, not what you may see.
- The server sends `canEdit` **per session** and `canCreate` / `canPublish` for the viewer,
  so the screen never guesses and a hidden button is never the only thing stopping an
  action.
- A mentor's own sessions are marked **Yours** and carry a teal edge, so they find their
  rows in a full week.
- Repeating sessions now list the whole org's, not just the viewer's, because somebody
  setting up Thursday needs to see Thursday is taken.
- Mentor nav: **Weekly sessions** replaces "Repeating sessions"; the old slots page is
  now "My one to ones", which is what it actually is.

**The permission rules, and why each one:**

| Action | Who |
|---|---|
| See the whole week | Every mentor and admin |
| Create a session | Mentors, if the toggle is on. Always admin |
| Edit a session | Whoever hosts it. Admin edits anything |
| Move a session to another host | Admin only — nobody takes a session off someone else |
| Release the week to learners | Admin only — publishing is editorial, not scheduling |

**New setting, Sessions > "Mentors can create sessions"**, default on. On, a mentor sets up
their own weekly sessions and one-offs and they appear on the shared week. Off, only the
office creates them and mentors see the week and take what they are given. Either way every
mentor sees the whole week and only an admin releases it. That is your "settings toggle or
admin-side setup" choice made switchable rather than decided in code.

## 13. Releasing a week now tells the learners

`publishWeek` flipped a flag and sent nothing. A learner found out only by opening the LMS
and noticing, which for the thing they most need to know about is the wrong way round.

Releasing now sends **one message per learner, per week** — not one per session — listing
the week's sessions with day, time, kind and topic. Each learner only gets the sessions in
their own scope, using the same audience rule their session list uses: track scope,
batch, and `openToAllBatches`. The toast reports how many were told.

## 14. A permission hole found on the way out

The old `/api/mentor/schedules/{id}/active` had **no ownership check at all**. Any mentor
could pause any repeating session in the org by passing its id — including another
mentor's, including the org-wide doubt clearing. The generation cron would then simply stop
producing it and nobody would be told.

Those three endpoints are deleted. Their replacements on `/api/week` go through
`assertMayEditSchedule`. `SessionBoardController` is deleted too, since it was a second
door to the same data with a different rule.

## Still open

Unchanged, plus your analytics ask which I have not started: tell me whether you want
cross-batch comparison, per-mentor outcomes, or a per-learner scorecard and I will build it.

# Fifth pass: combined analytics

## 15. Every learner's numbers on one row

The figures all existed and were scattered: course progress on one screen, test scores on
another, tasks on a third, attendance on a fourth, study minutes on a fifth. Nobody could
answer "is 56 doing worse than 55" or "are this mentor's learners finishing" without
opening five screens and holding it in their head.

New **Analytics**, at `/analytics`, for mentors and the office.

**One scorecard per learner**, carrying course progress (chapters watched against the
chapters in their bundle), test average, teach back average, tasks approved and overdue,
attendance percentage, study minutes over 28 days, days since last sign in, mocks
completed, projects approved, and the at-risk flag. Sortable on any column, searchable by
learner, batch, mentor or course, filterable to at risk, premium or batch.

**Three rollups of those same rows** — by batch, by mentor, by course. Building them from
the same rows as the table is what stops the summary and the detail quietly disagreeing,
which is the usual way a reporting screen loses people's trust.

**Scoped by role.** A mentor sees their own learners plus the totals to measure against,
and not the batch or mentor comparison tables. A league table of other mentors' numbers is
the fastest way to turn a reporting screen into something people manage rather than use.
An admin sees everything.

**Three judgements worth stating, because they change what the numbers mean:**

- **No single score.** Rolling progress, marks, attendance and effort into one figure
  invents a weighting nobody agreed and hides which of the four is the actual problem. The
  columns stay separate and the reader decides.
- **A blank is not a zero.** Somebody who has not sat a test yet is left out of the test
  average rather than counted as zero. Counting them would make every new cohort read as
  failing, and the first instinct on seeing that is to distrust the screen.
- **Nulls sort last** whichever direction a column sorts, because "does not apply" is not
  "worst".

One pass over the data builds everything: five queries rather than one per learner per
collection, which for seventy learners is the difference between five round trips and
three hundred and fifty on a screen people refresh.

# Sixth pass: simplifying the learner's side

## 16. A regression I had just introduced

Enforcing the feature toggles server side (item 10) broke two pages, because both fetched
first and hid afterwards. `Resources` called `/learner/jobs` and `/learner/case-studies`
unconditionally and then wrapped the *rendering* in `can(...)`; `Sessions` called
`/learner/calls` for every premium learner regardless of `biweekly_call`. With the server
now refusing those, a learner whose track excludes them got an error instead of a page.

Both now ask only for what their track includes. This is the standing hazard with
hiding-in-the-browser: the check lives in two places and only one of them was updated.

## 17. Every click was refetching the whole dashboard

`LearnerProvider` was mounted **per route**, wrapping each learner page separately. Every
navigation unmounted it and refetched `/learner/dashboard` and `/learner/continue-watching`
from scratch: two requests and a full skeleton flash on every single click, for data that
is identical on all of them.

Mounted once around the route tree. Moving between pages is now instant, and it costs
staff nothing because the loader returns immediately for any non-learner role.

This was the single biggest thing making the learner side feel slow.

## 18. Two different things both called Projects

The guided project system replaced the old form where a learner typed up work done
elsewhere. The old card was never removed, so a learner had:

- **Project** (`/learn/project-work`) — the briefed project with six stages
- **Tasks** (`/learn/projects`) — which still contained a second card called **Projects**,
  the old self-declared one, with a submit form that no longer led anywhere

Two menu entries with near identical names, the same icon, and confusingly similar URLs.
The old card and its form are gone. That page is now **Tasks** and only tasks; the menu
entries are **My project** and **Tasks**, with different icons.

## 19. The learner menu, twelve items down to nine

A learner is not an operator of this product. They are here to study.

| Was | Now |
|---|---|
| Sessions and calls + Recorded sessions | **Sessions**, with a Recordings tab |
| Information form (permanent menu item) | On the home checklist, where the rest of onboarding is |
| My study time (a page for four numbers) | A card on the profile, with a link to the detail |
| Project + Tasks | My project + Tasks, distinct icons |
| Messages using the intake icon | Its own icon |

Recordings only make sense next to the sessions that produced them: somebody looking for
last Thursday's doubt clearing was as likely to start under Sessions as under Recorded
sessions. It is the same component, rendered embedded, so there is one implementation.

**Every route still exists.** Nothing became unreachable — the command palette carries
all of them, and deep links still work. What changed is what earns a permanent place in
a menu somebody looks at every day.

**The menu is now feature aware.** An entry can name the features that would give it
something to show, and it is dropped when a learner's track includes none of them. The
menu no longer offers a page the server will refuse, which was the other half of item 16.

Mobile got the same treatment: four thumbs on the bar, each a different kind of thing —
what to study, when to turn up, what to hand in, what was briefed.

# Seventh pass: regrouping the staff menus

## 20. One vocabulary across every staff role

The staff menus were grouped by department: **Operations, Provisioning, Control, Run the
day, Work, Calendar, People, Sessions, Content, System**. Ten headings across three roles,
and the same object filed under a different one depending on who was looking.

Analytics sat under **Calendar** for a mentor. Projects sat under **Sessions** for an
admin. Sessions to publish sat under **Work** while every other session thing sat
elsewhere. Two people describing the same screen used two different names for where it
lived.

**Four headings now, same order for every staff role**, each answering a different
question rather than naming a team:

| Heading | Answers |
|---|---|
| **Today** | What is waiting on you right now |
| **Learners** | The people and their records |
| **Teaching** | The delivery machinery: sessions, projects, who teaches |
| **Setup** | Configuration and provisioning, touched rarely |

A role has fewer entries under a heading, or none. Nothing is filed by which team owns it.

**What moved, and why:**

- A mentor's **Today** is now the three queues plus the desk. Tasks, project reviews and
  sessions to publish are all "somebody is waiting on you", and they were spread across
  two headings.
- **At risk** joined Learners. It is a filtered view of the same people, not a separate
  kind of thing.
- **Analytics** left Calendar, which it was never part of, and sits with Learners for
  mentors and admins both.
- For super admin, **Teaching** is the catalogue — what exists to be taught, rather than
  this week's delivery of it — and the two desks moved into **Today**, since dropping into
  another role's screen is something you do at the start of a task, not configuration.

## 21. One week, one route

`/admin/board` and `/mentor/week` rendered the **same component** under two paths, labelled
**"Live session board"** for the office and **"Weekly sessions"** for mentors. One screen,
two names, which is how a team ends up describing the same thing differently in
conversation.

Now `/week`, with `/week/repeating` for the cadence behind it. Both old paths redirect, so
bookmarks and anything already sent round on WhatsApp still land. `/mentor/schedules`
redirects too.

Every role calls it **Weekly sessions**.

## 22. The command palette says what the menu says

The palette had drifted: "Course builder" for a screen the menu calls Overview, "Track
features" for Features and access, "Questions and answers" for Help and FAQs, "Live session
board" for Weekly sessions. Somebody typing what they read a moment ago would miss.

All three staff lists now use the menu's exact words, and the entries the menus dropped
during the learner simplification are all carried here, so nothing is unreachable.

Mobile bars got the same four-thumb treatment: for a mentor, Desk, Review, Learners, Week.
For an admin, Overview, Onboarding, Learners, Week.

# Eighth pass: super admin is the access controller

## 23. Super admin stops running other people's days

Removed from the super admin menu:

- **All learners** — the operational register belongs to the office
- **Admin desk** and **Mentor desk** — a way in to somebody else's screens

Those three blurred what the role is. Super admin decides what exists and who may reach
it; the running of it belongs to the people whose job that is. Both desks are still
reachable by signing in to those screens directly; they are just not presented as super
admin's daily work.

The menu now reads: **Today** (overview, analytics), **Access** (admin and mentors,
features and access), **Teaching** (the catalogue), **Setup** (form, FAQs, settings,
activity log).

**Access** is a new heading and it is the point of the role, so it stops being buried in
Setup alongside the FAQ editor.

## 24. Admin gets the feature toggles

**Features and access** now appears under the admin's **Learners** heading, and the route
and the API accept `ADMIN` as well as `SUPER_ADMIN`.

What a track includes is an operational decision the office makes week to week, so it sat
in the wrong place. Super admin keeps it too, under Access.

## 25. Video security removed, with the lockouts kept

The page is gone: route, all nav entries, the document title and the file.

**The sign-in lockout list moved to All learners** rather than going with it. Somebody
locked out is somebody who cannot sign in, and the register is already where the rest of
that lives: issuing credentials, resending them, resetting a password. It shows only when
there is somebody to let back in.

**One consequence worth stating plainly.** Video rotation went with the page, and rotation
was the answer to a leaked link: swap the underlying video ID and every copied URL dies.
The endpoint still exists (`POST /admin/access/videos/{id}/rotate`) but nothing reaches it,
so today a leak has no remedy in the UI. The playback log, the flags and the device release
are unreachable for the same reason.

If you want rotation back, the natural home is the super admin video settings screen, next
to where videos are registered. Say the word and it is a small job. Otherwise the endpoints
can be deleted outright so the API stops advertising something no one can use.

# Ninth pass: the breakages

## 26. Profile not loading

Reverted the study-time card I had added to the profile in the simplification pass. That
was the only change that page had, so it goes back to what worked, and study time stays
reachable at its own page.

Two hardening changes so that class of failure cannot blank a page again:

- `gates` is now defaulted to `{}` on destructure. The render walks `gates.form`,
  `gates.prereq` and `gates.call`; if that key is ever absent the whole component throws,
  React unmounts the tree, and the learner sees a page that never loads rather than an
  error. A default turns a blank screen into three unticked boxes.
- The resume fetch had no `.catch`. A failure there was an unhandled rejection.

## 27. rank had never rendered for anybody

`BatchSpace` read `rank` off the top of the learner context. **There is no such key**: the
payload carries it inside `batch`. The standing card was guarded by a value that was
always undefined, so it had never shown for a single learner since it was written.

Now `batch?.rank`. The same guard covers it being null when the leaderboard is off.

## 28. Premium learners were shown My batch

The nav entry was unconditional. `BatchSpace` itself always handled it correctly, with a
proper "you are on the premium track" panel, so it was only ever the menu offering a
destination that had nothing behind it.

Nav entries can now carry a track, and My batch is `BATCH` only. Premium sees Sessions and
Jobs under Cohort and nothing that is not theirs.

## 29. Messages removed

The page, its route, all nav entries and the two learner endpoints behind it are gone.

**Nothing that sends has been disconnected.** `MessageService.send` always wrote a row
*and* sent an email; only the in-app inbox is gone, so mentor notes, nudges and the weekly
session release all still reach the learner by email exactly as before. The row is still
written because it is the record of what was sent and the mentor's own view reads it.

Conversation lives on WhatsApp, and a second inbox was a place nobody checked.

## 30. One request instead of two

`LearnerContext` fetched `/learner/dashboard` and then `/learner/continue-watching`
separately. The dashboard already returns `continueWatching`, so the second call fetched
the same data again and added another way for the page to fail. Removed.

Combined with mounting the provider once rather than per route, the learner side went from
two requests on every single navigation to one request per session.

# Eleventh pass: why mentors could not see their learners

Four causes, not one. The first is the one that broke the roster outright.

## 40. `percent` was a Long and every reader cast it to Integer

`LearnerService.stats` computes:

```java
m.put("percent", totalChapters == 0 ? 0 : Math.round(watched * 100.0 / totalChapters));
```

`Math.round(double)` returns a **long**, and the ternary promotes the whole expression, so
`percent` went into the map as a `Long` **always**. Five places then read it back with
`(Integer)`, including the roster's own group average:

```java
.mapToInt(r -> (Integer) r.get("percent")).average()
```

That is a `ClassCastException`, not a wrong number. `/mentor/roster` threw a 500 as soon as
a mentor had a single learner with any progress, so the answer was not "some learners
missing" — it was the whole endpoint failing and the screen showing nothing.

The same cast sits behind the batch leaderboard and the learner's rank card, so those were
failing too.

Fixed at the source: `percent` and `avgQuiz` are ints. Every reader now goes through
`Number`, so a type change upstream can no longer take a screen down.

## 41. A batch was listed and then refused when opened

`myBatches` includes a batch when its mentor is visible **or when one of my learners is in
it**. `canSeeBatch` only checked the first.

So a mentor saw a batch on their list and got "That batch is not yours" on its roster — a
batch created without a mentor, or one holding a learner assigned to them directly, did
exactly this. Both rules are now the same union.

This is the identical fault this class had already fixed once for learners, and the comment
there says it plainly: a list and the check that guards it have to be the same rule, or one
of them is lying.

## 42. The learner record had two ways to 500 on real data

- `users.findById(...).orElseThrow()` — a learner whose user row is missing threw, and
  the mentor saw a record that would not load with nothing saying why. Every other builder
  on that page already copes with a null user, so the strict one only failed first.
- `Map.of("email", u.getEmail(), ...)` — **`Map.of` throws on a null value.** One learner
  without an email address and the whole record page 500s. Phone and WhatsApp were
  defended; email was not.

## 43. A landmine I planted two passes ago

Making the session toggles real used `featureService.enabled(...)`, which answers **no** for
a key that is not in the features collection.

The features seeder only fills an **empty** database. So on any existing install, a key
added later exists in the code and not in the data — and a plain `enabled` check would then
hide those sessions from every learner, with no way for an admin to work out why, because
the switch they would reach for is not on their screen either.

New `allowedUnlessConfiguredOff`: absent means unrestricted, present and off means off.
Used by the session-kind filter and the induction gate.

## 44. Null dates that took out the whole mentor side

`mentorIdsVisibleTo` is the first thing every mentor screen calls — the roster, the batch
list and the learner record all resolve visibility through it. It filtered cover rows on
`c.getFrom()` and `c.getUntil()` without a null check, so **one cover row with a missing
date would 500 every mentor screen at once**. Same in `canActOn` and the overlap check.

Also `MentorDeskService.row` summed study minutes filtering on `d.getDay()` with no null
check, which would fail the entire roster on one bad study row.

All skipped rather than thrown on. Bad data is bad data; it should not be a blank screen.

# Twelfth pass: assignments, end to end

Your four steps: staff attach an assignment to a chapter, the learner reads it and
downloads the material, the learner submits, the mentor reviews. Steps 1, 3 and 4 worked.
**Step 2 had never worked for a single learner**, and because it is the middle of the
chain the whole feature read as broken.

## 45. Learners can open the material

```java
if ("LEARNER".equals(me.role()) && !me.id().equals(f.getOwnerId())) { ... 403 }
```

The document is uploaded by staff, so `ownerId` is staff. **Every learner, every chapter,
every brief, dataset and rubric returned 403** from the day that guard was written. The
buttons rendered and none of them worked.

The rule was not wrong so much as too blunt. It replaced something worse — being signed in
was once the whole check, so a file id read off a task thread downloaded another learner's
notebook — and it fixed that leak by treating one rule as covering two different kinds of
file.

Two kinds, two rules:

- **Material** (`ASSIGNMENT`, `RESOURCE`) belongs to a chapter. Readable by any learner
  entitled to that chapter, and not by everyone who happens to be signed in.
- **Submissions** (`TASK`, `RESUME`, `PROJECT`) belong to a person. Owner and staff.

New `LearnerService.canOpenChapter` is the single answer to "may this learner open this",
so the file guard and the chapter page cannot reach different conclusions. The plumbing was
already there: `StoredFile.linkedId` has been the chapter id on upload all along.

## 46. Files say what they are

The payload sent bare ids, so three attachments rendered as three identical **Download**
buttons and the chapter editor listed `a3f91c02` instead of `rubric.pdf`.

One `FileService.viewsOf` helper — id, filename, size, extension — used by the learner's
brief, the chapter editor and the mentor's thread, so those three cannot drift. A file
that has gone from disk renders as unavailable rather than vanishing: an attachment that
disappears silently looks like a bug in the page.

The learner also now sees the **real due date** rather than "due in 7 days", and is told
when the next chapter is *not* waiting on this.

## 47. Chapter assignments can carry a rubric

`Assignment.rubricId` existed and the mentor's review screen renders a rubric properly, but
`AssignmentSpec` had no rubric field. So only an ad-hoc assignment a mentor typed by hand
could be rubric-scored.

That is backwards: the repeatable work every cohort does is exactly the half that benefits
from being marked the same way twice. `rubricId` on the spec, copied onto the row when it
is created, with a picker in the editor.

## 48. The mentor can see what they are marking

- **The chapter's own attachments** come through the review thread. It carried the brief
  text and the learner's upload and not the dataset the work was built from, so marking a
  notebook meant doing it without the question in front of you.
- **What the score is out of.** `marks` was on the spec and not in the mentor's payload,
  so they typed a number with no idea whether it was out of 20 or 100.
- **Filenames instead of "Download file 2"**, so three attachments can be told apart
  before opening them.

## 49. The queue is grouped by assignment

A flat list of learner and task title said nothing about what was being marked. Marking
eight submissions of the same assignment in a row is one job done consistently; marking
eight different ones interleaved is eight context switches and the scores drift apart.

Grouped by chapter, longest waiting first, with the attempt number on each row — a third
attempt at the same task is a different conversation from a first, and the mentor should
know before opening it.

## 50. Two settings that did nothing now do

- **`lockNext`** was editable and read by nothing, while `chapterComplete` blocked the next
  chapter on an approved task regardless. The switch was a lie in both directions. With it
  off, handing the work in is enough to move on and the mentor marks it in their own time:
  waiting days on a review queue to carry on studying is the wrong incentive to build in.
- **`allow`** was displayed and never checked. Enforced on submit now, naming the file and
  its extension. A mentor opening a `.docx` where a notebook was asked for is a wasted
  round trip for both people.

## 51. Mentors can attach an assignment

You asked for mentor, admin and super admin. Mentors now reach the chapter's assignment
section and the rubric endpoints, in the API and in the page.

**One line drawn deliberately.** A mentor sees the assignment card and nothing else on that
screen — not topics, not the test, not the teach back — and the server enforces the same
split. A chapter is shared content: rewriting its topics changes it for every cohort at
once, including ones already through it. Setting the work is a mentor's job; rewriting the
course is not.

If you want a mentor to attach material for *their cohort only*, that is a per-batch
override rather than a permission change, and a genuinely separate piece of work.

## 52. A shadowed field caught on the way out

`AssignmentService.submit` has a local variable called `files`, and the new `FileService`
field was also called `files`. Java compiles that happily — the local wins inside the
method — which is exactly why it is worth removing. The field is `fileService` now.
