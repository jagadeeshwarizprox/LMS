# Version 5, 11 October 2026: built for 20,000 learners, 1,000 active

Target: 20,000 stored learners, 1,000 active at once, one server. No screen changes
what it shows, except the paged lists and the Analytics table noted below.

## 1. Progress is stored, not recalculated

- Each learner record now carries its progress: percent, topics and chapters watched,
  average test, tasks and projects approved, last active. `ProgressSnapshotService` is
  the only writer; the fields are read only to every other save, so a gate or mentor
  change can never put back old numbers.
- Updated the moment progress changes: topic watched, test, teach back, task submit and
  review, project review, track/batch/course moves, sheet upgrades.
- A catalogue change (topic added, chapter released, course modules changed) marks that
  course's learners stale in one update; they recompute on next view, and a background
  sweep catches up the rest.
- Rank in batch and course is two count queries. The leaderboard is one sorted query for
  the top 10. Before, one batch page computed every learner in the course.
- Existing learners are filled in by `ProgressSnapshotMigration` in the background at
  start, 500 at a time; the app serves requests meanwhile.

## 2. Only the needed rows are read

- Learner, mentor and admin screens query by learner, mentor, batch, course, status or
  date instead of loading whole collections: learner home, chapter, batch space, video
  grant and watch save, continue watching, mentor desk, roster, at risk, team, queues,
  week board, recordings, register, onboarding board, overview, analytics, import.
- Related names, batches and courses are read once per screen, not once per row.
- Sign-in check: the session is still verified on every request, but its "last seen"
  is written at most once a minute instead of on every request.
- Mentor visibility walks the staff tree with one indexed query per level, cached 60
  seconds and cleared on any staff change.
- "Still onboarding" is a stored, indexed flag, kept in step on every learner save and
  repaired at start by `OnboardedFlagBackfill`.
- About 40 new indexes across learners, progress, assignments, slots, sessions, devices,
  watch rows, recordings, attendance, bookings and the logs.
- Analytics totals are database aggregations. The table now lists the at-risk learners
  furthest behind (up to 200) and says so; search anyone in All learners.

## 3. Paging

All learners, Onboarding board, Activity log, Access playback log and Mail log page 50
at a time with search and filters on the server (`components/Pager.jsx`).

## 4. Background jobs and runtime

- Nightly and background jobs work 500 rows at a time; the sharing check reads only the
  last 24 hours of plays.
- Tomcat 200 threads, Mongo pool 100, JVM heap at 75% of the container, Mongo cache set
  for an 8 GB server, nginx 4,096 connections.
- `DEPLOY.md` Sizing: 4 vCPU / 8 GB for 1,000 active, 8 vCPU / 16 GB for headroom, to be
  confirmed by the load test.

## 5. Load-test kit (`loadtest/`)

- `seed/seed.py`: 20,000 learners, 60 mentors, 40 batches, 3 courses, 400 topics, about
  290k progress rows and 145k watch rows; `--wipe` removes only seeded data.
- `k6/`: 900 learners, 80 mentors, 20 admins; 5 min ramp, 10 min hold. Pass: errors
  under 1%, learner reads p95 under 0.5 s, everything p99 under 2 s.
- `run.sh`: seed, restart the API so snapshots fill, run k6, write `results/`.

progress, sessions, logs...). 0 on this build.
