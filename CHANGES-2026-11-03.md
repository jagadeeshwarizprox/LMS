# Changes, 3 November 2026: onboarding sessions

Four things about the mentor's onboarding flow, each traced from the screen to the
database before anything was changed. Nothing new was built where something existed;
where nothing existed, the smallest thing that closes the gap was added.

Verified with `tools/offline-compile/verify.sh` (197 sources, 0 errors), every
`tools/check-*.py` (same two known items as the last build), and `vite build`. The
link parser was run against ten real link shapes. Not run: `mvn clean package`, because
Maven Central is not reachable from the build machine. Run it before deploying.

---

## 1. "Open now" did nothing

**Root cause.** On My desk, today's sessions were rendered as a plain row, and "open
now" was a label in it. The progress-call rows beside it were buttons; this one was
not, and had no click handler, so it read as a button and did nothing. Your slots had
no join control at all. The server side was fine: `POST /api/slots/{id}/join` already
existed, already let staff join outside the window, and is what the learner's Join now
button has always called.

**Fix.** The desk row is the button, and both it and a new Join on Your slots call that
endpoint and open what it returns, the same way the learner side does. The row says
what pressing it will do: open now, join, no link, cancelled, held. The link is still
fetched at click time and never listed.

**Found alongside.** `join()` never checked `cancelled`. A cancelled session handed out
its link to anyone, staff or learner, because the window was open and the mentor's
standing room is always live. It refuses now, with the reason. And the learner's slot
list dropped a session the moment it started (`startsAt > now`), so a learner two
minutes late, or who reloaded, could not find it although the window was open. The
list now keeps a session while its window is.

## 2. Nothing marked an onboarding session as completed

**Root cause.** There is no Zoom integration to report one. "ZOOM" is a label on
`MeetingRoom.provider`; the room is a pasted link, and no API, webhook or callback
exists anywhere in the backend. The only path that ever cleared the onboarding gate was
marking attendance PRESENT on the Attendance page, which few mentors knew was the step.
`Slot` had no held state of its own, and `Booking.status` declared ATTENDED and nothing
ever wrote it.

**Fix.** Confirmation comes from the host, after the fact, and from nowhere else.
`Slot` gains `heldAt` and `heldBy`. `POST /api/mentor/slots/{id}/held` marks everyone
booked present through the existing `mark()` path, so the gate clears the way it
always did and every screen that reads the gate (learner home, onboarding board, the
mentor's roster, analytics) agrees without a second write. Anyone the host lists as
absent is marked absent and keeps their gate.

The rules the request asked for, as the server enforces them:

- Joining, or opening the link, never marks anything. Only the held endpoint does.
- A second press is a no-op: it returns the session as it is, with no second
  attendance row and no second log line.
- A cancelled session cannot be held. A held session cannot be cancelled or moved; a
  follow-up is released as a new session. A session that has not started cannot be
  held.
- Rescheduling moves the date and leaves attendance and gates alone, as it did.

Mark as held appears on the desk once a session has started, and on Your slots, which
also shows each session's state (Upcoming, Not confirmed, Held, Cancelled). The week
board shows Held and stops offering edit on a held session.

## 3. No way to share an onboarding recording with a batch

**Root cause.** Three things. `VideoRefs.parse` refused `drive.google.com` outright,
with instructions to use YouTube instead. The publish form had no batch to choose, so
a recording went out with the kind's default audience, which for a one to one is
everyone. And a recording uploaded as a file was written with provider `UPLOAD`,
which no `VideoProvider` was registered under, so it answered "No player is configured
for this video" the first time anybody pressed play.

**Fix.** The link parser reads Drive file links (`/file/d/ID`, `open?id=`, `uc?id=`)
and folder links (`/drive/folders/ID`, with or without `/u/0/`), and the provider is
detected from the link rather than assumed. Three providers are new: `GOOGLE_DRIVE`
(plays in Drive's preview frame), `GOOGLE_DRIVE_FOLDER` (opens in Drive), and
`UPLOAD` (streamed by this server). The publish form on My one to ones has a batch to
share with, a description, and a video-only upload box that says the real limit. With
a batch chosen the recording goes out as that batch's induction recording, which is
the kind the library already files under Induction and the audience rule that keeps
it to that batch. The server refuses a batch share without a batch and refuses a batch
the mentor does not teach, the same way it refuses a session they did not run.

Learner access was already right: `VideoAccessService` re-derives the batch rule at
grant time, so a learner outside the batch never gets a grant, let alone a link. The
player branches on the grant's provider; the watermark stays on every branch.

What Drive does not buy: Drive decides who may open the file, not this application.
The mentor still shares the file or folder with the batch (anyone with the link, or the
accounts), or Drive's frame shows its own access request.

## 4. "Maximum upload size exceeded"

**Root cause.** `spring.servlet.multipart.max-file-size` was 25 MB and not
configurable, so any recording over it threw `MaxUploadSizeExceededException` before
`FileService` ran. That exception had no handler and fell into the generic 500, which
is the message reported. Underneath that: video extensions were not on the allowed
list at all, so even a small recording was refused as "not accepted"; the download
path read every file whole into memory, which for a recording means the heap; and the
upload control used `fetch`, which cannot report progress, so a long upload looked
stuck.

**Fix.**

- Two ceilings, both settings: `FILES_MAX_BYTES` (25 MB, documents and submissions,
  unchanged) and `FILES_VIDEO_MAX_BYTES` (500 MB, video uploaded as a recording). A
  video is only accepted under the RECORDING purpose and only a video is accepted
  there, so raising the recording limit does not raise what a learner may hand in.
- Spring's own ceiling is `UPLOAD_MAX_FILE_SIZE` / `UPLOAD_MAX_REQUEST_SIZE` (520 /
  530 MB), spooled to disk past 1 MB. nginx's is `UPLOAD_MAX_BODY`, passed through
  compose. `.env.example` explains how they relate.
- `MaxUploadSizeExceededException` is answered as a 413 that names the limit.
- `GET /api/files/limits` tells the control the numbers, so it refuses an oversize
  file before sending a byte and says the real limit in its hint.
- Uploads go through `XMLHttpRequest` with a progress bar per file.
- Uploaded recordings stream from disk by HTTP Range (`GET /api/video/stream/{grant}`),
  so seeking works and nothing is read whole. The address carries the grant the access
  log already writes: random, one viewer, one video, expiring, issued only after the
  entitlement check. That path is open in `SecurityConfig` because a `<video>` element
  cannot carry the bearer header; the grant is the credential.

## Database

No migration. `heldAt` and `heldBy` on `slots` are absent on existing rows, which reads
as not held. `Booking.status` now takes the ATTENDED value it always declared.

## Still open

- Zoom cloud recording links are not playable and never were; the old placeholder
  promised them. Download from Zoom and upload here, or put the file on Drive.
- Automatic completion from Zoom needs a Zoom Marketplace app with webhook
  verification and a way to map meeting ids to sessions. None of that exists; marking
  held is the confirmation until it does.
- On Railway, the frontend calls the API domain directly, so `UPLOAD_MAX_BODY` on
  nginx is not in the path. The API's `UPLOAD_MAX_FILE_SIZE` is what applies there.
