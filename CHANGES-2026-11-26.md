# Changes, 26 November 2026: the content sheet

Course content can now be managed from one Excel sheet. The LMS reads it, adds what is
new, applies what was edited, and never deletes anything. Manual editing in Modules and
chapters works exactly as before, and both can be used on the same course.

Verified with `mvn clean package` (passes), `tools/offline-compile/verify.sh` (209
sources, 0 errors), every `tools/check-*.py` (no new findings; the two that remain are
from earlier builds: one call in `TaskThread.jsx` and `FormFieldSeeder`), `vite build`,
and an end-to-end run of the whole sync lifecycle against a real backend and Mongo
(31 checks, all passing; see **How it was tested**).

Not tested: automatic sync from a real Google Sheet (there was no public test sheet to
point it at; the same code path was tested through upload and Sync now, and its error
handling against an unreadable Google link), a learner downloading a fetched file, and
the new screen in a browser (it builds; nobody has clicked through it yet).

## Super admin: Teaching → Content sheet (new screen, `/super/content-sheet`)

**Download template.** An .xlsx with the agreed columns: S.no., Name of course, Name of module,
Chapter name, Title, One line, Code runner(python/none), Video link, Notes, Code,
Dataset, Slides, Written note. A workbook may have several tabs; every tab with this
header row is read, and other tabs (instructions, notes) are ignored.

**Google Sheet link.** Paste the sheet's link; it must be shared as "Anyone with the
link can view". Save reads the sheet once, so a sheet that is not shared, or is not in
the template's shape, is refused with the reason there and then. Turn on **Sync
automatically** and the LMS checks the sheet every 10 minutes (5 to 1440, adjustable) and
syncs only when its content has changed.

**Upload the sheet.** For working without a link. **Check first** reports what would
change and writes nothing; **Upload and sync** applies it.

**Sync now / Preview changes.** Pulls the linked sheet (if set) and syncs it, or
reports what would change without changing anything.

**Last sync.** New, changed, unchanged, no longer in the sheet, and rows with problems,
with **See details** and **Retry failed**.

**Sync history.** Every run: when, how it started (upload, Sync now, automatic, retry,
restore), by whom, and the result. **Details** lists each row the run touched, with what
was done to it and, for problems, why. Unchanged rows are counted, not listed.

**Versions.** A copy of the sheet is kept every time its content changes (not every
time it is checked). Each can be downloaded. **Restore** makes an older copy current and
syncs it; automatic sync is switched off at the same time so the linked sheet does not
immediately overwrite the restore.

## How a sync decides what to do

- A row is identified by **module + chapter + title** (case and extra spaces ignored).
- **Name of course** is optional. When filled, it must match a course in Courses and
  pricing (the sheet never creates a course, since a course carries pricing and access).
  An unknown name makes the row invalid. A module named in a course is looked for in that
  course first, and a module not yet in it is added to it; the run says so, and says
  whether learners can see it (only if the module is published).
- Module and chapter are found by name. If missing they are created **as drafts**, the
  same as in the builder, and the run says so: publish them in Modules and chapters.
- A new row whose title matches a topic already in that chapter **adopts** it rather
  than making a duplicate. Adoption never overwrites: what the topic already has (one
  line, video, notes and so on) is kept, and only empty parts are filled. Edits made in
  the sheet after that are applied.
- For every row the LMS remembers a fingerprint of each cell. On the next sync only
  cells whose fingerprint changed are processed, so a fifth video added to a course
  touches the fifth row and nothing else.
- **Video link**: YouTube, Google Drive or Cloudflare Stream, stored as a reference
  exactly as the builder does. YouTube links are checked first: a deleted or private
  video, or one with embedding turned off, is reported and not attached.
- **Notes, Code, Dataset, Slides**: each link is downloaded into LMS storage and
  becomes a material, so learners never need access to the original. Drive file links,
  Google Docs (saved as PDF), Slides (as .pptx) and Sheets (as .xlsx) are understood.
  Several links in one cell (separated by spaces, commas or new lines) become one
  material each. A file goes under the kind its type belongs to: a notebook in the
  Notes column is filed under Code, and the run says so.
- A link removed from a cell **hides** the material it made; putting the link back shows
  it again. Nothing is deleted.
- **Written note**: a text material, updated in place when the cell changes.
- **Order**: topics follow S.no inside their chapter (decimals work: 1.5 sits between 1
  and 2). Topics added by hand keep their places.
- **A row removed from the sheet** is reported as "no longer in the sheet" on every
  run. Its topic, materials and learner history stay in the LMS.

## Errors and retries

- A row missing module, chapter or title, or repeating another row's module, chapter
  and title, is reported as invalid and skipped.
- A broken link (404), a file that is not shared, a file type the LMS does not keep, an
  oversized file (over `FILES_MAX_BYTES`, 25 MB by default), an unsupported video host,
  or a code runner value other than python or none fails **that cell only**. Everything
  else in the row and the run goes ahead, and the run is marked "Done with problems".
- A failed cell's fingerprint is not recorded, so the next sync or **Retry failed** tries
  exactly those cells again and nothing that already worked.
- One sync runs at a time; a second request is refused until the first finishes.

## Security

- The screen and its API are open to the same roles as catalogue editing: Admin and Super
  Admin on the API (`/api/super/catalogue/content-sheet/**`), Super Admin in the menu.
- Links are fetched over https only, with the address checked on every redirect. Any
  link resolving to a private, loopback or link-local address (localhost, the database,
  cloud metadata) is refused. Size is capped while downloading, and every fetched file
  passes the same extension and size checks as a manual upload.
- Copies of the sheet are stored as files with the purpose `CONTENT_SHEET`, which
  learners cannot download. Fetched materials are stored with the purpose `RESOURCE`
  against their chapter, so the existing rule decides who may download them.

## What changed in the code

- New: `service/contentsheet/` (`ContentSheetService` the sync, `ContentSheetParser`
  reading and the template, `LinkFetcher` downloads), `web/ContentSheetController`, and
  four collections: `content_sheet_config`, `content_sheet_versions`,
  `content_sheet_rows` (per-row sync state), `content_sheet_runs` (history).
- `FileService.store` now has a second form that takes bytes rather than a browser
  upload; the browser upload goes through it, so both meet the same checks.
- Frontend: `pages/superadmin/ContentSheet.jsx`, route and menu entries (sidebar, mobile
  menu, command palette), and `downloadPath` in `api/client.js` for file downloads from
  any endpoint.
- Tools: `check-wiring.py` understands `downloadPath`; `check-scans.py` allows reading
  every content-sheet row (one per sheet row, catalogue sized); `check-java-imports.py`
  no longer reports `InterruptedException` (it is in `java.lang`); `check-generic.py`
  exempts `ContentSheetParser.java`, whose template header and code runner values name
  the runner by its value. POI stubs in `tools/offline-compile/stubs` cover the calls
  used.

## How it was tested

A local backend on an empty database, driven through the API by a script:

1. The template downloads and carries the agreed headers.
2. First upload: four topics created, with a YouTube video attached, a CSV dataset and a
   PDF fetched into storage, and a written note.
3. The same sheet again: four unchanged, and no new version kept.
4. Preview of a sheet with two more rows: both reported, nothing written.
5. Sync: two added (one with S.no 1.5), four unchanged, and every existing topic's
   materials still the same records.
6. Two cells edited: exactly two rows updated; the written note updated in place.
7. A 404 dataset link, a link to localhost and a Vimeo video: each reported on its own
   cell, the run marked "with problems", the other rows untouched.
8. Retry: only the three rows with failed cells processed.
9. The broken link fixed: only that cell fetched.
10. A row with no chapter and a duplicate row: both reported invalid.
11. A topic made by hand in the builder, then named in the sheet: adopted (same id), its
    one line kept.
12. A row deleted from the sheet: reported, and its topic and notes still there.
13. Order: 1, 1.5, 2, 3, 4, 5, then the hand made topic.
14. Restore of the first version: recorded as a new version; topics only in later
    versions reported and not deleted.
15. All original topic ids unchanged throughout, which is what keeps watch history,
    progress, tests and assignments.
16. A sheet link into the private network refused; an unreadable Google Sheet refused
    with a reason.

A first run of this script found a real bug that is fixed in this build: links were
used as Mongo map keys, Mongo refused them because of the dots, and the same file was
fetched again on every sync.

## Noticed, not changed

Topic materials uploaded by hand in the chapter builder are saved against the topic id,
but the download rule for learners (`FileController`, `canOpenChapter`) expects a chapter
id. Reading the code, learners would be refused those downloads. Not tested with a
learner account, and not changed here. Files fetched by the content sheet are saved
against the chapter, so they are not affected.

## Phase 1: testing on the live LMS with a Google Sheet

Rehearsed first on a local copy: an "Agentic AI" course with a published module, a
published chapter and two topics with videos. A sheet with two new video rows previewed
as two new rows on the right module and chapter, synced as two topics in that chapter
with their videos, and left the two existing topics with the same ids, videos and
materials and in their places. A third row added to the same sheet imported only that
row (one added, two unchanged). A row naming a course that does not exist was refused
and no course was created. A real Google Sheet (Google's public sample) was fetched
through Google's export redirect and parsed. All checks passed.

**Before testing on the live course: what new topics do to learners.** A chapter counts
as finished only when every topic in it has been watched. Adding topics to a published
chapter, by the sheet or by hand, keeps every learner's watch history and progress
records, but lowers their percentage and, for learners who had finished that chapter,
makes it unfinished again until they watch the new videos, which can hold back the
chapters after it. To test without touching learners, name a **new chapter** in the
sheet (for example "Sheet sync test") inside the Agentic AI module: the sync creates it
as a draft, so learners never see it, and everything below can still be checked.

**Steps**

1. Deploy this build. On Railway, check that `FILES_DIR` sits on a persistent volume;
   without one, sheet backups (and fetched files) disappear on every redeploy.
2. Download the template from Teaching → Content sheet. Make a Google Sheet from it.
   Fill two rows: S.no., Name of course (exactly as in Courses and pricing), Name of
   module and Chapter name (exactly as in Modules and chapters), Title, and a YouTube or
   Drive Video link. Share the sheet: General access → Anyone with the link → Viewer.
3. Paste the sheet's link on the Content sheet page and press Save. It should say how
   many rows it read. Leave automatic sync off for now.
4. Press **Preview changes**, then **Details**: two "New" rows, on the right module and
   chapter, nothing invalid.
5. Press **Sync now**. Details should show two topics created with "Video attached", and
   no "Created module" or "Created chapter" unless you chose a new test chapter. Open the
   chapter from the details: the two topics play.
6. Check existing content: the chapter's other topics are where they were, and a
   learner's record shows the same watched topics as before.
7. Turn on **Sync automatically**, set the interval to 5 minutes, Save. Add a third row
   to the Google Sheet. Within about 5 minutes (plus up to a minute), a run marked
   "Automatic" appears: 1 new, 2 unchanged.
8. Nothing is deleted at any point. Removing test rows from the sheet only reports them;
   removing the test topics or chapter from the LMS is a separate decision.

## Phase 2 (not built)

Clearing existing course content and rebuilding it from the sheet is not implemented and
nothing here deletes LMS content. When it is wanted, it needs its own approval and an
explicit, confirmed admin operation with a backup first.
