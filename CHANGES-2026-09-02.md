# Change set, 2 September 2026

Everything below is in this build. The frontend was built with Vite and compiles clean;
the backend passes every structural checker in `tools/` (imports, accessors,
constructors, service calls, derived queries, routes, wiring, scope, a11y).

---

## 1. The copy URL path is closed

`frontend/src/components/SecurePlayer.jsx`, rewritten.

"Copy video URL" and "Copy embed code" are drawn by YouTube inside a cross origin
iframe. Nothing we run can reach into that document to remove a menu item, and the
previous approach covered two corners while leaving the rest of the surface live: a
right click anywhere else still opened the menu.

The iframe is no longer interactive at all.

- `controls: 0`, `disablekb: 1`, `fs: 0` on the player, so YouTube renders no control
  bar, no logo link, no share affordance and no keyboard handler.
- A shield covers the entire player surface at `z-index: 3` and takes every pointer
  event. `contextmenu`, `auxclick`, middle click, drag and selection are all cancelled
  on it. `pointer-events: none` on the iframe as a second layer.
- Because the pointer never reaches the iframe, the menu carrying the link can never
  be opened from anywhere on the video.
- Everything a learner needs was rebuilt underneath: play and pause, a scrub track with
  buffer, back and forward ten, a speed menu, volume with mute, and fullscreen taken on
  our shell so the watermark and the shield go fullscreen with it.
- Keyboard shortcuts bound on our shell: space and k, j and l, arrows, m, f.
- The watermark now rotates between four resting places on a timer, so a crop cannot
  lose it.

What this does not do: the video id still moves over the network to build the player.
The permanent fix is signed playback (Cloudflare Stream), which the video service is
already shaped for. Until then the library is protected by short lived grants, unlisted
uploads, and one click rotation in Access and sharing.

## 2. Live session board

New: `pages/admin/LiveBoard.jsx`, `web/SessionBoardController.java`, board methods in
`ScheduleService`.

The old model assumed one mentor owns a session forever, which contradicts how the org
runs. A learner belongs to one mentor. A live session does not: the host rotates.

- `SessionSchedule` gained `hostRotation`, so week n is taken by roster position n
  without anybody editing the schedule. Weeks are counted from a fixed epoch, so
  regenerating slots lands on the same host it did before.
- Audience per session: everyone, premium only, batch only, optionally tied to one
  batch.
- Draft and release. The week is held as draft and released in one action; unreleased
  sessions are invisible to learners.
- Per occurrence host reassignment, leaving the schedule behind it alone.
- Seven day grid, colour coded by kind, with seats booked against capacity.
- Session kinds are now first class: doubt clearing, recap, project, industry, live,
  induction. Industry sessions carry a speaker.

**Cross batch fix.** `LearnerService.openSlots()` used to drop every slot carrying a
batch id, so any schedule created against a batch was silently invisible to everybody
else, contradicting the lifecycle doc. A slot is now only private to a batch when it
says so.

**One to one stays with the mentor.** Booking a `DOUBT` or `ONE_ON_ONE` slot against
another mentor is refused. Every other kind is open to whoever is hosting.

# Interface pass

Not a redesign. The navy, blue and teal are sampled from the logo, Sora and Inter are
already the right pairing for a product read on a phone during a commute and on a
desktop during a review. Changing any of that would cost recognition and buy nothing.
What follows is the work that makes dense screens read as ordered rather than busy.

## A palette breach, mine

The session board, mentor doors, batch cards and redo banner shipped earlier today
using `var(--pib-red, #E0212F)`. `--pib-red` is not defined in this product, so the
fallback rendered zPROx red inside a ProITBridge interface. Every instance is gone.

In its place, track colour is now a system rather than a per-component decision:
`--premium` is the navy tile, `--batch` is the blue wordmark, and the avatar, the tag,
the door, the batch card and the session card all read from those two. The same learner
used to be navy in one list and something else in the next.

The session board's six kind colours were an arbitrary rainbow. They are now the three
logo colours at different depths, with amber held back for industry sessions, which are
the one kind that cannot run until somebody is booked.

## One type scale

There were twenty-two distinct font sizes in the stylesheet, most a hundredth of a rem
apart. Seven steps now, as tokens, and small text stops at 12px because this is read on
phones. Applied across the new surfaces and the shared page, card, stat and table.

Micro labels are sentence case instead of tracked-out capitals. Capitals at 10px are
slower to read and were doing no work that the position in the layout wasn't already
doing.

## Hover means clickable

`.card-pib` lifted and shadowed on hover everywhere, including on cards that are pure
reading surfaces. Movement under the cursor on something inert is the commonest reason
an interface feels fussy. The lift is kept only where the whole card is an action.

## Tables

Full hairline grids replaced with a horizontal rule per row, a quieter header, and
consistent row padding. Below 720px the roster stops being a table: each row becomes a
stacked block with its column name in front of the value, which is the only readable
shape at that width. A six column table on a 390px screen is a horizontal scrollbar
nobody finds.

## One focus ring

Four different focus treatments across the product, now one, on `:focus-visible` only,
so a mouse click does not leave a ring behind it.

## One moment

Finishing a chapter opens the next one, and that was a state change with no
acknowledgement: the row stopped being grey while the learner was looking somewhere
else. A newly opened chapter now settles open once, in place, with the lock turning
off. It fires only on the transition, never on load, and never under
`prefers-reduced-motion`.

That is the only non-user-triggered motion added. Everything else that moves is
answering something the person did.

## Also

Touch targets go to 40px on coarse pointers. Dark mode gaps on all the new surfaces are
closed. `tone="ok"` and `tone="warn"` were being passed to `Stat`, which expects a
colour value and silently ignored both, so three status figures were rendering in plain
ink.

# Fix: a mentor opening a learner was signed out

Two defects, and it took both to cause it.

**The learner record asked for things a mentor is not allowed to have.** Opening
`/mentor/learners/{id}` fired two admin-only requests:

- `GET /admin/learners/{id}/mentor-history`, from the record page
- `GET /admin/learners/{id}/move-options`, from `MovePanel`, which was rendered for
  every viewer and had **no `.catch` at all**

Neither is a request a mentor made. They fired on their own, on every open, against
`/api/admin/**`, which `SecurityConfig` restricts to admins.

**The client tore down the session on any 401 from any request.** The handler could not
tell "your session is over" from "you cannot have that one thing", so a refused
background request wiped the token, fired `pib:signed-out`, and dropped the mentor at
the sign-in screen. From the mentor's side, clicking a student logged them out.

## What changed

1. On a 401 the client now re-checks `/auth/me` with the same token before discarding
   anything. If the session still answers, the 401 belonged to that one endpoint and is
   raised to the caller as a permission error. Only a session that has genuinely
   stopped working signs anyone out. `X-Session-Ended` is still trusted immediately,
   because that is the server saying the session is gone.
2. `MovePanel` renders and fetches for admins only, and its fetch has a catch. Moving a
   learner between tracks, batches and courses was already an admin action; it was
   only the request that leaked.
3. The mentor-history fetch is gated on the same check rather than being made and
   swallowed.

## To confirm on your side

Open the browser network tab, sign in as a mentor, click a student. Before this fix
there were two red `/api/admin/...` rows. After it there are none, and no request to
`/api/admin/**` should appear from any mentor screen.

# Learner status, visible to the mentor

## What was being recorded, and who could see it

The product already tracked all of this. Almost none of it reached a mentor.

| Recorded | Where | Mentor could see it |
|---|---|---|
| Position in every video, per learner | `WatchPosition` | No. Nowhere in the product |
| Which topics inside a chapter are finished | `Progress.watchedTopicIds` | No. Only a module-level bar |
| Whether a video was finished or abandoned | `WatchPosition.completed` | No |
| When they last watched anything | `WatchPosition.updatedAt` | No |
| Test score, attempts, best score | `QuizAttempt` | Partly. Raw attempts on one tab |
| Teach back score | `Progress.conceptCheckScore` | Partly |
| Task status per chapter | `Progress.taskStatus` | Partly, on a different tab |
| Attendance, per session | `Attendance` | No. Written and never read back |
| Minutes studied per day | `StudyDay` | Only a chart, only on the record |
| Notes the learner wrote | `ChapterNote` | No |
| Questions asked the assistant | `AiInteraction` | No |

The learner record drew one progress bar per module. One bar per module cannot answer
"has he watched the videos", which is the question a mentor asks first.

## What was built

**`LearnerProgressService`**, a new service, because `MentorService` already takes
nineteen constructor arguments. It assembles the whole picture: module, chapter, topic,
and for each topic the video, the position reached, and when.

**Four states instead of a tick.** "Not ticked" was hiding two completely different
situations, so a topic now reports one of:

- **Watched**, finished
- **Almost finished**, past ninety per cent and stopped, which is nearly always an
  interrupted session rather than an abandoned one
- **Started**, a position was recorded and they did not come back
- **Not opened**, nothing at all

A learner with four abandoned videos and a learner with four untouched ones used to look
identical on the roster. They need different conversations.

**A Learning tab** on the learner record: watched, opened-not-finished, never-opened and
minutes remaining across the top; then every module, expandable to every chapter, then
every topic with its own progress bar, percentage and date. Each chapter row carries its
test score and attempt count, teach back score, task status and whether the learner kept
notes. Below that, recent sessions with present, late or missed, and the questions they
have been asking.

**Both learner lists** gained a Videos column: how many finished, how many started and
abandoned, and how long since they last watched anything. This is on `learnerRow`, so
every list of learners in the product carries it.

**Attendance is read back.** It was being written by mentors and never shown to anyone,
including the mentor who wrote it. Rate, present, late and missed now sit on the record.

## A note on cost

`rowStats` is built from three queries per learner rather than by walking the course
tree, because a mentor with forty learners loads forty of these at once. A watch position
already knows whether its video was finished, so the course structure is not needed to
count them. The full tree is built only when one learner's record is opened.

# Projects

## What was there

A form. A learner typed the title, summary and tools of something built elsewhere,
attached files or a repository, and a mentor approved it. No brief, no data, no
checkpoints, nothing for a Saturday session to be about. It is kept, because a learner
with real industry work should not have to redo it, but it cannot be taught against.

## What was built

Two things, kept apart on purpose: a **catalogue** holding the content, and a **run**
holding one learner's position in it. That split is what lets a brief be corrected
mid-cohort without disturbing anybody's submissions, and lets the same project run for
every batch without being copied.

### Six stages, fixed

| Stage | Asks for | Due |
|---|---|---|
| Brief and kickoff | Nothing. Read it, get the data, join the kickoff | Day 0 |
| Scope and approach | What they will build, what they are leaving out, how they will know it worked | Day 5 |
| Checkpoint one, foundation | Data in and cleaned, environment running, skeleton working end to end | Day 12 |
| Checkpoint two, core build | The deliverable | Day 21 |
| Review and rework | A response to the review. Nothing new is built here | Day 26 |
| Demo and handover | Recorded walkthrough, README, repository | Day 30 |

Fixed rather than authored per project, so a mentor learns one flow and a batch grid
compares across projects. Due dates are offsets in days from enrolment, so the same
project runs for every batch unedited. What an author changes is what each stage asks
for, when it is due, and which rubric scores it.

### A stage advances only when a mentor says so

Everything else follows from that. A learner cannot reach the demo having built nothing.
A redo is not a special case, it is a stage sent back. And the batch grid means
something, because every position on it was decided by a person.

Sending a stage back requires a reason. The API refuses `CHANGES` with an empty note.

### Screens

**Learner**, `/learn/project-work`. The brief, who the work is for, what finished looks
like, the data they have been given. A rail of six stages down the left showing where
they are, one stage open with what it wants. On a redo the feedback is pinned above the
upload box with the version number they are about to send. Every attempt is kept.

**Mentor**, `/mentor/projects`. The review queue, oldest first, because a learner waiting
four days for a checkpoint has stopped working. The review drawer shows the latest
attempt with earlier ones folded away, scores against the stage's rubric with the
weighted total computed live, and one decision: approve and open the next stage, or send
back.

**Batch grid.** One row per learner, one column per stage, one square per cell. A column
of amber is a stage the mentor is behind on. A row of grey is somebody who stopped. It
answers "who is stuck at scoping in week three" by looking rather than by opening twenty
records.

**Super admin**, `/super/projects`. The project builder: brief, client context, success
criteria, data files, level, expected hours, which courses it attaches to, and per-stage
editing.

### Connections made

- An approved project opens the mock interview for a batch learner, which is the
  lifecycle document's rule. This previously hung off the old declared-project approval.
- Stage rubrics use the existing `Rubric` model with its weighted criteria. Two rubrics
  were seeded at first run with `scope = PROJECT` and there has never been a way to edit
  them; the builder now points at them and the existing rubric endpoints are finally
  called by something.
- Enrolment is admin, since it is an operations decision like a batch move. A whole
  cohort goes onto a project in one action.
- Email on enrolment and on every review outcome.

### Decisions held from the plan

Teams are supported in the model and default to off, with the reason written into the
builder: a team of four hiding one person who did nothing is the commonest failure in
cohort projects, and it needs per-person visibility before it is worth turning on.

## Not yet done

Project sessions on the live board are not yet tied to a project's current stage, and the
portfolio entry on approval is still part of the open portfolio work.

# "Something went wrong, cannot load"

That exact sentence comes from `ApiErrorHandler`: it is the reply to any unhandled
exception, a 500. Two separate faults made it impossible to act on.

## Why nobody could tell what broke

**The server wrote no log line.** The catch-all handler returned a message and swallowed
the exception without logging it. A mentor reporting a blank screen left nothing behind
on the server to look at.

**The client threw away the cause.** The 500 body already carried the real exception in
`detail`, and `client.js` read only `error`, so every unexpected failure reached the
screen as the same seven words.

Both fixed. The stack trace now goes to the server log with the method and path that
caused it, and the reply carries the exception type and message, which the client shows.
Whatever is failing on your instance will now name itself.

## The likely cause, fixed

A chapter carries three nested blocks, `test`, `teachback` and `assignment`. They are
initialised in the class, but a chapter saved to Mongo before one of them existed
deserialises with it **null**, and every caller writes `c.getTest().isEnabled()` with no
guard. One old chapter row turns the whole learner record into a 500.

The setters now refuse null, so the field defaults survive deserialisation, and the new
progress code guards each one anyway.

Eight further null paths in the new progress code are now guarded: a watch position with
no timestamp, a study day with no date, a progress row pointing at a deleted chapter, a
watch position with no video reference, and null-safe ordering on attendance and doubts.
Any one of them was a 500 for the whole list.

## The roster had none of the new numbers

`/mentor/roster` is built by `MentorDeskService.row()`, not by `MentorService.learnerRow()`
where the watch statistics were added. Two row builders for the same thing. Until they
are merged, both now carry the same stats, so the Videos column stops showing a dash.

## The desk tiles are links now

Learners assigned, tasks to review, projects to review and at risk were plain numbers. A
mentor read "6 at risk" and then had to go and find the six. Each tile now opens the list
it counts.

That exposed a related defect: the tiles and the premium door linked to
`/mentor/learners?track=PREMIUM` and `?filter=risk`, and `MyLearners` ignored the address
entirely, so every one of them landed on the same unfiltered list. The page now reads the
filter and the track from the address, keeps them in step as you change them, and has a
track selector next to the existing chips.
