# Moving off local disk

Nothing outside this folder knows where bytes live. Every document holds a `fileId`,
every download goes through `FileService`, and `FileService` goes through
`StorageProvider`. Switching is one class and one config line.

## What it takes

1. Add the SDK to `pom.xml`. For S3 or any S3-compatible service, including Cloudflare R2:

```xml
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>s3</artifactId>
    <version>2.28.16</version>
</dependency>
```

2. Write `S3Storage implements StorageProvider` in this folder, annotated:

```java
@Component
@ConditionalOnProperty(name = "lms.files.provider", havingValue = "S3")
```

Four methods: `put`, `get`, `delete`, `key`. Implement `supportsDirectUrl` as `true` and
`directUrl` with a presigned GET, which takes large downloads off the API entirely.

3. Set `FILES_PROVIDER=S3` plus the bucket, region and credentials.

4. Move the existing files. `aws s3 sync ./data/files s3://your-bucket/` is enough,
because the storage key is the filename on disk and the object key in the bucket. Nothing
in Mongo changes.

## When to bother

Local disk is the right answer while there is one server and somebody is backing it up.
Move when any of these is true:

- The API runs in a container on ephemeral storage, so a restart loses everything
- There is more than one instance, and the other one cannot see these bytes
- Datasets and slide decks have grown past what you want on the application server

## What must not change

The storage key is generated by `FileService`: random, never the filename, never anything
a caller can influence. A provider stores exactly what it is given under exactly that key.
Any implementation that derives a path from user input reintroduces a traversal bug that
this design exists to prevent.
